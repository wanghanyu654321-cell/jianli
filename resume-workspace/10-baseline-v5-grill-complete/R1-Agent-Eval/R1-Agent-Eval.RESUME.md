### 杭州人瑞网络科技有限公司｜评测专家（淘天 Data Agent）｜2025.09–2026.06

- **Data Agent / Query 评测：** 参与 Query、Data Agent 输出、召回结果和商品相关性评测，将用户意图、商品语义及业务规则落到具体 Case 判断；同时接触多轮上下文、工具调用结果、执行步骤完整性及最终回答是否解决用户问题等 Agent 行为评测。
- **开放题 / Path Eval：** 面对没有唯一标准答案的开放问题，结合既有指标选取高分 / 低分答案，对比不同 Layer / Path 的差异，观察意图、工具选择、工具结果和异常处理等关键节点；明显工具错误可直接识别，工具选择等非显性问题则结合路径与最终结果判断，再将稳定差异沉淀为后续判断规则。
- **Rubric / 规则治理：** 新任务进入执行前，不直接将上游规则原样下发，而先结合实际 Case 检查定义是否清楚、业务上下文是否足够、边界是否过宽及场景是否覆盖；完成必要对齐后，再转化为下游可稳定执行的判断口径、示例和培训内容。补充规则时同时控制复杂度，避免为了减少少量错误不断增加新的理解成本和歧义。
- **Bad Case / 根因分析：** 对重复偏差不简单归因于执行人员，而结合 Case、人员理解方式与规则本身判断问题来自业务知识、业务上下文、规则表达、判断边界还是执行流程，再分别补充背景、收窄边界、增加示例或调整执行方式，并通过后续复测 / 抽检验证改善。
- **QA / 争议 Case：** 常规承担约 **10% 抽检**及质量复核，通过抽检识别高频分歧和异常模式；规则内能够稳定判断的问题直接推进修正，无法稳定裁定的争议 Case 则整理核心争议点后提交上级确认。
- **质量治理结果：** 围绕反复出现的问题累计参与沉淀 **10+ 份 SOP / 规则 / 执行文档**，持续收敛可执行边界；部分任务一致性约 **80%→95%**，复杂任务约 **60%→85%**。
- **版本效果 / A/B：** 参与执行层灰度桶 / A/B 测试及相关取数，结合 **DAU、CTR、转化、业务水位**观察版本变化和异常情况，并整理反馈。
- **搜索 Query 理解：** 接触 Query 预处理 / 理解 / Rewrite、召回、Filter、排序、SERP 与反馈链路，并使用 L1/L2/L3 相关性分级参与判断，帮助区分 Query 理解、召回和商品相关性等不同问题。

## 项目经历

### 个人 Agent 项目｜数字前台：门店微信接待 / 知识问答 / 预约线索 / 人工接管

**项目背景：** 面向小型门店 / 服务型商家的线上第一接待和私域承接。针对微信入口中重复咨询响应不及时、预约 / 线索意向容易丢失、异常问题缺乏稳定转人工流程等问题，第一阶段聚焦：

**微信入口 → 第一接待 → 知识问答 → 预约 / 线索意向 → 轻量业务状态 → 人工接管 → 后续跟进。**

项目已完成**微信部署与实体本地生活门店 POC，并开始在接待场景中使用**。随着 Agent 从工程验证进入门店流程，质量问题不再只是“最终答案对不对”，还需要判断：什么时候应该回答、什么时候必须停止、Tool 是否有权执行、业务动作有没有真正发生，以及修复一个问题后有没有破坏其他行为。

**本人负责：** 问题定义、方案边界、验收标准、评测设计、Bad Case 归因、方案取舍、测试验收和项目状态判断；通过 AI Coding Agent 协作完成实现与 Review。

**技术栈：** TypeScript / Node.js｜React｜Python / FastAPI｜PostgreSQL 16 / pgvector｜Docker Compose｜RAG / 知识库｜Prompt / 指令｜Tool Use｜Agent Runtime｜Eval / Regression / Harness｜CI

- **评测集 / 场景覆盖：** 将质量判断从最终答案扩展到知识依据、路由、Tool Use、无答案 / 歧义和权限行为；以 **40-case 冻结主测试集**覆盖可回答、无答案和歧义场景，并保留 **60-case Blind Holdout** 等分层验证，用于检查修改是否只对已知 Case 有效。
- **边界与负向测试：** 加入租户 / 门店隔离、未批准知识、失效 / 退役版本等 Negative Cases，验证“检索到了”不等于“当前有资格回答”；即使技术上检索成功，只要范围、状态、版本或歧义条件不成立，仍要求拒答或转人工。
- **Bad Case 根因分析：** 评测失败后不直接调 Prompt，而先判断是否拿到正确知识、知识是否允许使用、Tool 权限是否成立、业务动作是否执行、业务流程是否正确；只有底层链路正常而模型行为仍偏差时，才优先调整 Prompt / 指令。
- **回归测试 / 版本判断：** 修复目标 Bad Case 后重新跑冻结测试集与 Blind Holdout，同时检查正常回答、无答案、歧义、权限和 Safety 行为是否退化，用来区分整体提升、局部修复还是针对已知 Case 的表面改善。
- **Tool Use / 业务动作验收：** Ticket / 人工接管等工具调用不以模型文本或单次 Tool Call 作为成功证明，而按 **权限通过 → 状态写入 → 持久化 → scoped read-back → 验收** 判断，避免把“模型说完成”误判为业务动作已经完成。
- **Trace / 执行轨迹分析：** 项目通过结构化 Trace 观察意图、规划 / 决策节点、工具选择、工具结果和错误处理，并记录首 Token 延迟、工具调用数量等运行指标，用于定位多步骤执行中的异常；正式工作中的开放题 / Path 对比方法单独保留在人瑞经历中，不混写成项目已实现的自动轨迹评分。
- **Eval Harness / CI：** 将 Case、Config、Runtime、Evaluator 与 Report 分开管理，检查测试集 / 配置 / 知识版本、Case 完整性和运行状态；回归评测接入 CI，缺失 Case、重复 Case、配置不匹配或运行中断时不进入版本通过判断。
- **Quality Gate / Case 回流：** Safety、Knowledge、Retrieval、Runtime 等风险分别保留 PASS / FAIL / BLOCKED 结论，不用单一综合分数掩盖硬失败；门店 POC 后产生的咨询、预约 / 线索、人工接管和异常 Case 逐步回收到 Dataset 与 Regression Set，形成从现场问题到后续版本验证的闭环。
