项目已完成微信部署与实体本地生活门店 POC，门店开始在接待场景中使用。随着 Agent 进入门店接待流程，质量问题不再只是“最终答案对不对”，还需要判断：**什么时候应该回答、什么时候必须停止、工具是否有权执行、业务动作有没有真正发生，以及修复一个问题后有没有破坏其他行为。**

**技术栈：** TypeScript / Node.js｜React｜Python / FastAPI｜PostgreSQL 16 / pgvector｜Docker Compose｜RAG / 知识库｜Prompt / 指令｜工具调用｜Agent 运行时｜评测 / 回归测试 / 测试框架

- **Eval Dataset：** 将质量判断从最终答案扩展到知识依据、路由、工具权限、无答案、歧义和权限行为；在 **40 个冻结案例（24 个可回答 / 8 个无答案 / 8 个歧义）**基础上，进一步保留 Safety、**100-case Robustness**、**60-case Blind Holdout**、Knowledge 与 Retrieval / Runtime 等分层回归，不把单一综合分数作为版本判断。
- **Negative Cases / 权限边界：** 加入租户 / 门店隔离、未批准知识、失效 / 退役版本等负向测试用例，验证“检索到了”不等于“当前有资格回答”；即使检索成功，只要范围、状态、版本或歧义条件不成立，仍要求拒答或转人工。
- **Bad Case 根因分析：** 评测失败后不直接调整 Prompt，而先判断是否拿到正确知识、知识是否允许使用、工具权限是否成立、业务动作是否执行、业务流程是否正确；只有底层链路正常而模型行为仍偏差时，才优先调整 Prompt / 指令。
- **Regression / Holdout：** 修复目标 Bad Case 后重新跑冻结测试集与 Blind Holdout，同时检查正常回答、无答案、歧义、权限和 Safety 行为是否退化，用来区分整体提升、局部修复和针对已知样本的表面改善。
- **Tool Use / Action Acceptance：** Ticket / 人工接管等业务动作不以模型文本或单次 Tool Call 作为成功证明，而按 **权限通过 → 状态写入 → 持久化 → scoped read-back → 验收** 判断，避免把“模型说完成”或工具返回成功误判为业务动作已经完成。
- **Trace / Trajectory Eval：** 首 Token 延迟、工具调用数量、KV Cache 等运行指标可通过埋点记录，但轨迹评测还需要 Agent 框架提供结构化 Trace，至少能看到意图、规划 / 决策节点、工具选择、工具结果和错误处理。开放题不存在唯一标准路径，因此先按轨迹相似度判断是否进入可比集合，再结合关键节点标记、路径差异和最终结果做评分反馈；明显错误看工具执行，隐性问题还要看工具选择。
- **Eval Harness / Run Integrity：** 将 Case、Config、Runtime、Evaluator 与 Report 分开，检查测试集 / 配置 / 知识版本、Case population、completion marker 是否一致，并识别缺失 Case、重复 Case、配置不匹配或运行中断；只有运行完整且证据可回溯时才进入质量判断，避免测试流程本身制造误判 PASS。
- **Quality Gate / Version Decision：** 将目标 Case、Regression、Acceptance 与 Run Integrity 共同用于版本判断；Safety、Knowledge、Retrieval、Harness、Runtime 等风险分别保留 PASS / FAIL / BLOCKED 结论，不用单一综合分数掩盖权限、业务状态或安全问题。
- **Case 回流 / Regression Set：** 完成微信部署与门店 POC 后，开始收集咨询、预约 / 线索、人工接管和异常案例，并逐步纳入测试集与回归测试。当前使用时间与样本量仍有限，尚不足以形成稳定的线上质量结论。

**项目状态：** 已完成微信部署与实体本地生活门店 POC，门店开始使用；长期稳定性、规模化复制、生产环境 SLA 与稳定线上质量指标仍待持续验证。

**技术栈：** TypeScript / Node.js｜React｜Python / FastAPI｜PostgreSQL 16 / pgvector｜Docker Compose｜RAG / 知识库｜Prompt / 指令｜工具调用｜Agent 运行时｜评测 / 回归测试 / 测试框架

- **产品定位：** 主要面向一线店员 / 客服和管理侧，优先解决及时接待、常见问题稳定回答、预约 / 线索承接，以及复杂、歧义和高风险问题稳定转人工。
- **产品范围：** 第一阶段不做完整 CRM，也不做全自动客服 / 全能数字员工。轻 CRM 只保留支撑预约、Ticket / 人工接管的最小业务状态，人工接管本身被定义为正常产品路径，而不是“Agent 失败兜底”。
- **MVP / 优先级：** 优先建设知识库 / FAQ、预约意向、Ticket / 人工接管和必要业务状态：知识库解决最高频重复咨询，预约意向承接私域转化节点，Ticket / 人工接管保证异常进入人工，而权限和真实状态写入决定这些能力能否真正进入业务流程。功能优先级不是按“AI 程度”排序，而按场景频率、业务价值、风险和可验收性判断。

### 数字前台 Agent｜业务风险场景 → 工程机制 → 微信部署 / POC → 验证

**业务背景：** 面向微信等私域入口的线上第一接待，核心业务链为：

**知识库 / FAQ → 预约 / 服务意向 → 持久化业务状态 → Ticket / 人工接管 → 人工**

项目将真实业务风险和失败场景转化为可测试、可部署、可进入真实门店业务流程的工程机制。

**技术栈：** TypeScript / Node.js｜React｜Python / FastAPI｜PostgreSQL 16 / pgvector｜Docker Compose｜RAG / 知识库｜Prompt / 指令｜工具调用｜Agent 运行时｜评测 / 回归测试 / 测试框架

- **RAG / 知识问答：** 实现过程中首先遇到的问题是“检索成功并不代表业务上可以回答”。因此检索只产生候选证据，再由 Node 结合审批状态、版本、租户 / 门店范围、来源和歧义情况决定是否允许回答；证据不足或无法唯一判断时拒答或转人工。
- **工具调用 / 权限控制：** 模型负责理解用户意图并提出动作，但身份、成员关系、能力权限、业务范围与最终写权限由服务端决定，避免 Prompt 或模型输出直接获得业务授权。
- **服务职责：** Python / FastAPI 被限制为内部候选证据服务，只负责返回候选证据，不负责批准知识、扩大业务范围或改变业务状态；最终授权保留在掌握身份、业务上下文和持久化状态的 Node 主应用侧，避免形成多个权威中心。
- **业务状态：** Ticket / 人工接管等业务动作只有完成 **权限检查 → 写入 → 持久化 → 按权限范围回读** 后才确认成功，解决模型文本中的“已完成”与真实系统状态不一致的问题。
- **幂等 / 并发：** 单纯检查幂等键是否存在无法覆盖并发竞态，因此进一步通过业务范围内幂等控制和预占 / 事务思路处理两个并发请求同时越过检查点的问题，降低重复业务副作用。
- **超时处理：** Agent 运行时设置最大轮次、工具调用次数和超时限制；超时不仅意味着前端返回失败，还需要通过取消机制和迟到事件隔离，防止请求结束后后台继续产生业务动作。
- **RAG 验证：** pgvector / FastAPI / Node 的跨服务集成已验证数据与接口链路打通，但不能证明真实 Query 的语义检索质量已通过；Hosted Embedding 和真实业务场景下的检索质量验收因此保持独立状态，不用“系统打通”替代“效果已经好”。
- **Bad Case 根因分析：** Agent 出错后先判断知识库 / 证据、Prompt、路由、工具、权限还是业务流程，再修改对应层，避免长期使用 Prompt 覆盖底层问题。
- **回归验证：** 冻结测试集、负向测试用例、留出测试集、回归测试和业务结果验收共同用于判断 Prompt / RAG / 工具 / 业务流程修改是否破坏已有行为。
- **性能取舍：** Semantic Selector 做过真实模型、未见样本留出测试、顺序鲁棒性和延迟测试；历史 30 次调用约 **P50 7.35s、P95 16.67s**，与当前整体 10s / 单工具 2s 的同步预算不匹配，因此不进入主路径。结论不是“技术没用”，而是当前使用位置不成立。
- **微信部署 / POC：** 已完成微信部署与实体本地生活门店 POC，门店开始实际使用；系统从本地 Demo / 集成测试进入门店业务流程，高并发、长期稳定性和生产环境 SLA 仍待验证。
- **系统集成：** 主干已集成 PostgreSQL、React、Docker、FastAPI / pgvector，并完成微信真实渠道接入与门店 POC；工程验证继续覆盖干净环境、数据库迁移、重启后状态保持、权限隔离和核心业务流程，用来区分“系统能启动”“真实渠道能接入”和“业务动作能被正确验收”三个不同层级。
- **上线后验证：** 门店开始使用后，重点跟踪 Query、异常、人工接管、状态一致性、超时和依赖失败，再将问题回收到 Bad Case → 根因分析 → 修改环节 → 回归测试。当前样本仍有限，检索质量、长期可用性和大流量容量仍待验证。
