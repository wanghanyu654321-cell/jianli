# R4｜AI 产品运营 / 智能服务产品运营

## 求职方向

**AI 产品运营 / 智能服务产品运营 / AI Product Ops**

## 个人总结

具备从用户与场景反馈中发现问题、结合数据和业务上下文定位原因，并推动产品、规则或业务流程调整的经历。

早期电商工作并不只是经营执行。在朗臻长期通过市场、Search 和消费者反馈判断产品机会，在老板确定产品大方向后进一步落细需求并与工厂 / 产品开发侧推进；在今宜根据市场变化重新调整商品目标用户和核心表达，再通过短视频、直播、CTR / CVR / ROI 持续验证。后续淘天 Data Agent 工作进一步强化了从执行者行为、复杂 Badcase 和规则边界中发现产品 / 流程问题的能力。

数字前台 Agent 将这些能力迁移到 AI 产品场景：从**实体商家微信等私域入口缺少稳定线上第一接待**的问题出发，先明确目标用户、使用场景、产品范围、MVP、验收标准和后续演进逻辑，再决定具体功能形态。项目现已完成微信真实部署与实体本地生活门店 POC，门店开始实际使用，因此产品判断也从内部 Case / Launch Readiness 进入真实门店 业务流程、真实咨询与后续使用反馈驱动的迭代阶段。

## 工作经历

### 杭州人瑞网络科技有限公司｜Data Agent 评测｜2025.09–2026.06

- **用户 / 执行者问题发现：** 参与 Query、Data Agent Output、召回 和 相关性 评测，同时承担规则理解、执行口径、QA 和复杂 Badcase；面对质量偏差时继续追问执行人员为什么会这样理解，而不是只修最终结果。
- **Context 与产品 / 流程问题识别：** 发现部分质量问题并非简单“不熟规则”，而来自业务概念缺失、Context 不足或规则本身留有过大解释空间，因此结合真实 Case 和执行反馈补充必要 Context，并优化任务说明。
- **隐性反馈与需求收集：** 除正式培训和会议外，也通过日常沟通了解执行人员真正卡住的位置，识别正式场合未必主动暴露的理解偏差，再将这些问题重新转化为 Context、示例、规则边界或流程调整。
- **问题归因与流程优化：** 对重复 Badcase 区分知识背景、规则表达、判断边界和 业务流程 问题，再决定是补 Context、改说明、增加示例还是收窄判断空间，而不是把所有质量问题都归结为执行人员问题。
- **QA 与验证闭环：** 通过约 **10% 抽检**及后续 QA 观察调整是否真正降低分歧；累计参与沉淀 **10+ 份 SOP / 规则 / 执行文档**，部分任务一致性约 **80%→95%**、复杂任务约 **60%→85%**。
- **版本与数据反馈：** 参与灰度 / A/B 及 DAU、CTR、转化、业务水位等指标观察，将执行反馈和数据变化一起作为版本判断输入。

### 杭州今宜商贸有限公司｜抖音代运营兼职｜2024.11–2025.07

- **产品定位与用户场景：** 结合市场变化发现健身轻食 / 营养健康需求增长，因此将玉米包从常见宝宝辅食表达调整到健身轻食场景，并重新组织核心卖点和使用情境；重点不是简单改文案，而是重新判断用户为什么购买这个产品。
- **内容实验与产品表达验证：** 先通过短视频测试不同卖点、视觉和使用场景，观察哪类表达更容易获得点击和后续转化，再将表现更有效的方向迁移到直播，并参与双机位方案设计，使产品定位、内容表达和直播承接形成连续验证。
- **数据诊断与迭代：** 本人直接承担巨量千川投流，根据 CTR、CVR、ROI、素材和直播承接判断问题位于内容、流量还是转化层；CTR 高但 CVR 低时不直接判断素材成功，而继续检查流量匹配、产品表达、价格和直播承接，再决定下一步优化对象。
- **0→1 项目推进：** 协同约 **6 人直播团队**推进内容、主播、排期、投流和复盘；同一新盘账号月 GMV 从早期约 **7 万提升至接手首月约 43 万**，本人核心贡献集中在投流、产品 / 内容判断和方案推进，不将团队结果全部归因为个人。
- **经营反馈闭环：** 持续结合店铺、流量、营销和交易数据观察产品表达、内容与经营结果之间的关系，而不是只以内容数量作为评价标准。

### 浙江朗臻网络科技有限公司｜电商运营 → 宠物项目运营管理｜2022.03–2024.07

- **用户需求与市场发现：** 新商品 / 新业务启动前结合市场规模、Search 需求、关键词增长和竞争环境判断机会；平台数据之外，也直接联系消费者补充真实使用场景，但不把少量个体反馈直接视为整体市场结论，而是与搜索趋势和经营数据交叉使用。
- **需求验证边界：** 将消费者反馈更多用于发现潜在问题和需求，将 Search / 市场数据用于判断需求是否具有更广泛代表性，避免用少量反馈直接做产品结论。
- **产品需求与协同推进：** 宠物项目中老客户持续出现的猫粮需求被识别为值得继续验证的产品信号，并成为产品线扩展输入；老板确定产品大方向后，本人基于市场、Search、消费者反馈和经营信息进一步落细具体产品要求，并与工厂 / 产品开发侧推进。
- **Search 与产品反馈：** 通过 Query、关键词、商品标题和详情属性持续优化产品与需求匹配，推动核心商品搜索排名由百名外进入 **细分类目前 10**；Search 数据同时作为产品需求反馈，而不仅是流量工具。
- **经营 / 产品问题诊断：** 商品表现不达预期时，结合流量、点击、转化、商品和链接状态判断问题，再决定优化表达、调整商品还是测试新的产品方向；另一核心 SKU **接手首月内日 GMV 约 1,000+→15,000+**。
- **项目经营与跨团队推进：** 后续负责约 **5 个跨平台店铺**，对 GMV、利润率、DSR 和渠道结果直接负责，并协同内容、客服、供应链、品牌、平台和工厂推进问题解决。

## 项目经历

### 数字前台 Agent｜用户需求 → 产品定义 → MVP → 微信部署 / POC → 产品迭代

**项目背景与问题定义：** 项目聚焦实体商家线上第一接待的空白：很多商家线下已有人员接待，微信又天然沉淀了大量私域关系，但用户进入线上入口后，重复咨询、预约意向和异常问题仍高度依赖人工即时响应，意味着“有私域流量”并不等于“有人能够稳定承接”。

产品因此收敛为：

**第一接待 → Knowledge / FAQ → Booking / Service Intent → 轻量状态 → Ticket / 人工接管 → Human**

**技术栈：** TypeScript / Node.js｜React｜Python / FastAPI｜PostgreSQL 16 / pgvector｜Docker Compose｜RAG / Knowledge｜Prompt / 指令｜工具调用｜Agent 运行时｜Eval / 回归测试 / Harness

- **产品定位与目标用户：** 主要面向一线店员 / 客服和管理侧，优先解决及时接待、常见问题稳定回答、预约 / 线索承接，以及复杂、歧义和高风险问题稳定转人工。
- **产品范围与边界：** 第一阶段不做完整 CRM，也不做全自动客服 / 全能数字员工。轻 CRM 只保留支撑 Booking、Ticket / 人工接管 的最小业务状态，Human 人工接管 本身被定义为正常产品路径，而不是“Agent 失败兜底”。
- **MVP 与功能优先级：** 优先建设 Knowledge / FAQ、Booking Intent、Ticket / 人工接管 和必要业务状态：Knowledge 解决最高频重复咨询，Booking Intent 承接私域转化节点，Ticket / 人工接管 保证异常进入人工，而权限和真实状态写入决定这些能力能否真正进入业务流程。功能优先级不是按“AI 程度”排序，而按场景频率、业务价值、风险和可验收性判断。
- **需求设计与开发协作：** 将 Target User、用户旅程、Scope、Non-goals、业务流程 和 Acceptance Criteria 按产品需求 / PRD 结构组织，再通过 AI Coding Agent 协作实现；开发过程中持续用真实 业务流程 / Case 反查需求是否被正确实现，不把“写完需求”本身当作产品完成。
- **Badcase 驱动产品迭代：** 遇到问题不直接归因于模型，而先判断问题来自需求定义、Knowledge / RAG、Prompt、业务流程、权限还是业务状态，再回到对应产品层修改，避免把所有问题都变成 Prompt Tuning。
- **方案取舍与产品判断：** Semantic Selector 虽然技术上更复杂，但历史真实调用约 **P50 7.35s、P95 16.67s**，不符合当前同步 Runtime 预算，因此没有因为“更 AI”就进入主链；技术能力只有在用户价值、质量和使用成本同时成立时才进入产品。
- **微信部署与真实门店 POC：** 已完成微信真实部署与实体本地生活门店 POC，门店开始在真实接待场景中实际使用；这使产品验证从“内部 Case 能否通过”进入“真实用户是否会这样问、门店 业务流程 是否能承接、异常是否能顺利转人工、业务状态是否真实发生”的现场阶段。
- **真实使用与迭代入口：** 门店开始实际使用后，后续产品输入将优先来自真实咨询、预约 / 线索、人工接管、异常场景和一线人员反馈，再判断应该改 Knowledge、Prompt、业务流程、权限还是产品范围。当前真实使用时间与样本仍有限，因此不把“开始使用”包装成留存、效率或业务转化已经提升。
- **上线后指标与验证设计：** 继续关注有效 Knowledge 回复、预约 / 线索承接、正确 人工接管、无答案 / 歧义 边界、首轮响应和人工重复处理等指标；当前已经进入真实使用阶段，但尚未形成足够稳定的 post-launch 指标结论，因此仍坚持“指标设计 / 开始采集 ≠ 已验证业务提升”。
- **产品演进逻辑：** 第一接待稳定后，再根据真实门店使用中持续出现的问题决定是否增加服务提醒、定时触达和私域促活等轻量能力，而不是预先构建一个庞大的营销 / CRM 产品。

**当前状态：** 已完成微信真实部署与实体本地生活门店 POC，门店开始实际使用；产品已从 MVP / Launch Readiness 进入真实门店使用与反馈阶段。长期留存、规模化复制、商业付费、生产环境 SLA 及上线后业务指标仍待持续验证。
