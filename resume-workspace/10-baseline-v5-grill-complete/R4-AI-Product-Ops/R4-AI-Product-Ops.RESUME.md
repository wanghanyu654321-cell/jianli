## 核心项目

### 数字前台 Agent｜门店微信接待 / 知识问答 / 预约线索 / 人工接管

**项目属性：** 个人 Agent 项目。  
**项目状态：** 已完成**微信部署与实体本地生活门店 POC**，门店开始在接待场景中使用。

**项目背景：** 门店已有微信等私域流量，但重复咨询、预约 / 线索和异常问题高度依赖人工即时处理，需要稳定的线上第一接待和人工接管机制。

**本人负责：** 问题定义、需求拆解、方案边界、验收标准、评测设计、Bad Case 归因、方案取舍、测试验收和项目状态判断；通过 AI Coding Agent 协作完成实现与 Review。

- **问题定义 / 用户场景：** 从“门店线上接待不稳定”出发，先明确一线店员 / 客服和管理侧真正需要解决的高频问题，再决定产品能力，而不是从“做一个 Agent”反推需求。
- **MVP / 产品范围：** 第一阶段不重建完整 CRM，也不扩展为全自动客服或全能数字员工；优先保留知识问答、预约 / 线索、轻量业务状态和 Ticket / 人工接管，按场景频率、业务价值、风险和可验收性确定优先级。
- **需求拆解 / 业务流程：** 将目标用户、用户旅程、知识问答、预约意向、业务状态、人工接管和异常处理拆成可实现的流程，并通过真实 Case 反查需求与系统行为是否一致。
- **AI 方案 / 边界设计：** RAG 检索只产生候选知识，再结合门店范围、知识状态、版本和歧义决定回答、拒答或转人工；Agent 可理解意图并提出动作，但最终权限和写操作由服务端控制。
- **验收 / 质量闭环：** 将正常回答、无答案 / 歧义、Tool Use、权限、业务状态和人工接管分别验收；通过冻结测试集、Blind Holdout、Regression、Eval Harness / CI 检查修改是否破坏已有行为。
- **方案取舍：** Semantic Selector 历史测试约 **P50 7.35s、P95 16.67s**，不符合当前同步运行预算，因此未进入主路径；技术方案必须同时满足用户价值、质量、风险和运行成本。
- **POC / 用户反馈：** 微信部署和门店 POC 后，真实咨询、异常、人工接管和一线反馈开始回流到后续需求、Bad Case 和版本迭代，形成从场景 → 使用 → 反馈 → 改进的闭环。
