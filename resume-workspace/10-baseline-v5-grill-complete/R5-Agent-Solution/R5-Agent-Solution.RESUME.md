## 个人总结

具备从真实业务问题出发设计 Agent 业务流程、工程机制和评测验证的项目实践。个人数字前台 Agent 已完成 **Node.js、FastAPI、PostgreSQL / pgvector、React、Docker、RAG、Tool Use、评测 / 回归**等应用链路，并完成微信部署与实体本地生活门店 POC，开始进入真实门店接待流程。

工程重点不是单纯“把模型接起来”，而是解决业务系统真正会遇到的问题：**知识能不能用、模型有没有权执行、业务动作是否真实发生、异常如何回滚 / 转人工、修改后是否破坏已有行为**。Data Agent 正式评测经历进一步提供 Query、召回、相关性、复杂 Bad Case、规则转译和质量治理能力。

同时具备业务和项目底座：在朗臻从电商运营逐步承担项目运营管理，负责约 **5 个跨平台店铺**，年度整体 GMV 约 **1,500 万**；在今宜参与新盘 0→1，同一账号月 GMV 从早期约 **7 万提升至接手首月约 43 万**。因此工程判断通常从业务风险和失败场景出发，再选择技术方案。

## 项目经历

### 数字前台 Agent｜门店微信接待 / 知识问答 / 预约线索 / 人工接管

**项目属性：** 个人 Agent 项目。

**业务背景：** 面向微信等私域入口的线上第一接待，核心业务链为：知识问答 → 预约 / 服务意向 → 轻量业务状态 → Ticket / 人工接管 → 人工跟进。

**技术栈：** TypeScript / Node.js｜React｜Python / FastAPI｜PostgreSQL 16 / pgvector｜Docker Compose｜RAG｜Tool Use｜Agent Runtime｜Eval / Regression / CI

- **RAG / 知识边界：** 检索只产生候选知识，再结合审批状态、版本、租户 / 门店范围、来源和歧义情况决定回答、拒答或转人工，避免把“检索成功”直接等同于“允许回答”。
- **Tool Use / 权限控制：** 模型负责理解意图并提出动作，身份、成员关系、能力权限、业务范围与最终写权限由服务端控制。
- **业务状态 / 持久化：** Ticket / 人工接管等动作需完成 **权限检查 → 写入 → 持久化 → scoped read-back → 验收** 后才确认成功。
- **可靠性控制：** 对幂等、并发竞态、最大轮次、工具调用次数、超时、取消和迟到事件进行约束，避免请求结束后继续产生业务副作用。
- **系统集成：** 主干集成 PostgreSQL、React、Docker、FastAPI / pgvector，并完成微信渠道接入；验证数据库迁移、重启后状态保持、权限隔离和核心业务流程。
- **评测 / 回归：** 使用冻结测试集、负向测试、Blind Holdout、回归测试和业务动作验收判断 Prompt / RAG / Tool / Workflow 修改是否破坏已有行为。
- **性能 / 架构取舍：** Semantic Selector 历史 30 次调用约 **P50 7.35s、P95 16.67s**，与当前同步运行预算不匹配，因此未进入主路径。
- **微信部署 / 门店 POC：** 已完成微信部署与实体本地生活门店 POC，门店开始实际使用；现场 Query、异常、人工接管和状态问题持续回流到 Bad Case → 根因分析 → 修改 → 回归。

### 杭州人瑞网络科技有限公司｜评测专家（淘天 Data Agent）｜2025.09–2026.06

- **Agent / Data 质量评测：** 参与 Query、Data Agent 输出、召回和商品相关性评测，长期处理正常案例、歧义案例和复杂 Bad Case。
- **规则转译：** 通过案例理解业务上下文、定义和边界，再转化为执行层可理解的标准、案例和判断要求。

- **搜索链路：** 接触 Query Understanding / Rewrite、召回、Filter、Ranking、SERP 等 Search 链路。
