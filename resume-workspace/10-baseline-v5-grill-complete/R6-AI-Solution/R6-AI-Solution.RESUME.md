## 工作经历

### 杭州人瑞网络科技有限公司｜Data Agent 评测｜2025.09–2026.06

- **复杂业务规则理解与转译：** 承接上游业务规则和任务要求后，先理解业务目标、数据口径和判断边界，再转化为下游 BPO 可以执行的标准和培训内容，减少上游业务语言与执行理解之间的偏差。
- **需求澄清与问题反馈：** 执行前主动发现规则定义不清、业务上下文不足或场景覆盖缺口，并集中与上级确认；执行过程中持续同步阶段、发现的问题和待确认事项。
- **复杂问题解释：** 对重复 Bad Case 结合执行人员理解、规则本身和业务上下文判断问题来源，再推动规则、示例、培训或执行边界调整；无法稳定裁定的问题则整理核心问题后升级确认。
- **规模与交付结果：** 单项任务下游 **10+ 人、每周约 5,000–10,000 条**；累计参与沉淀 **10+ 份 SOP / 规则 / 执行文档**，部分任务一致性约 **80%→95%**、复杂任务约 **60%→85%**。
- **版本与数据沟通：** 参与灰度 / A/B 及 DAU、CTR、转化、业务水位等指标观察，并汇总异常及版本反馈。

### 杭州今宜商贸有限公司｜抖音代运营兼职｜2024.11–2025.07

- **业务目标与需求判断：** 项目开始阶段直接与老板确认当前更偏 GMV、ROI、利润还是新盘增长，再据此决定投流、内容、达人合作和利润容忍度，使方案围绕真实业务目标而不是固定模板展开。
- **方案取舍：** 新盘早期发现内容和直播承接能力仍有明显提升空间，因此优先投入资源改善底层转化，再逐步放大付费流量，而不是用更多预算覆盖基础问题。
- **达人 BD 与合作筛选：** 新链接缺少历史销量、权重和成熟素材时，直接通过微信 / 电话推进达人合作，以产品 / 内容匹配、历史销售和合作意愿判断优先级。
- **商业条件与利润取舍：** 冷启动阶段不追求达人渠道短期利润最大化，在退款、货损等基本成本风险可覆盖前提下，可以适当让渡利润换取首批销量、商品权重和起盘速度。
- **合作结果：** 达人合作 **单月销售额合计 10 万+**；同一新盘账号月 GMV 从早期约 **7 万提升至接手首月约 43 万**。
- **跨团队推进：** 协同约 **6 人直播团队**在业务目标、资源条件和数据结果之间持续推进策略与执行。

### 浙江朗臻网络科技有限公司｜电商运营 → 宠物项目运营管理｜2022.03–2024.07

- **平台商务与合作条件：** 直接参与京东小二合同条件、毛利结构、合作方式、活动资源和成本条件讨论，同时考虑平台希望获得的价格 / 活动力度与商家利润和长期经营空间。
- **商业方案取舍：** 当平台资源要求与商家毛利发生冲突时，通过推广投入、固定扣点、活动货值等不同要素重新组合合作条件，例如适当增加推广预算以争取更合理的固定扣点；最终重大条件由老板确认。
- **活动与资源方案：** 参与直接费用型、货值型活动的投入规模和合作条件讨论，并结合库存压力通过平台活动 / 资源置换推进消化。
- **工厂 / 产品需求沟通：** 在老板确定产品和合作大方向后，根据市场、用户和经营信息进一步落细产品需求，与 To-B 工厂及产品开发侧推进具体事项，并持续同步合作内容和进展。
- **市场与产品理解：** 新商品启动前先结合市场、Search 需求和关键词增长判断机会；消费者反馈只作为补充，不直接替代整体市场数据。
- **经营与供应协同：** 后续负责约 **5 个跨平台店铺**，对 GMV、利润率、DSR、月 / 季目标及渠道结果直接负责，同时参与大促备货、供应排期、库存周转和爆单后的跨仓调拨。
- **业务规模与多方协作：** 业务年度整体 GMV 约 **1,200 万–2,000 万**，协同内容、客服、供应链、品牌、京东小二及工厂 / 产品开发等多方推进经营事项。

## 项目经历

### 数字前台 Agent｜客户问题 → 解决方案 → 微信部署 → POC 交付

**业务问题与价值判断：** 很多实体商家拥有线下接待能力和微信私域流量，但线上第一接待和后续意向承接较弱。项目先围绕业务方最关心的问题确定方案范围：

**有人来能不能接住、回答能不能信、预约 / 线索会不会丢、动作会不会错、出了问题能不能找到人。**

当前已完成微信真实部署与实体本地生活门店 POC，门店开始在真实接待场景中实际使用。这能够证明方案已经进入真实业务流程，但仍不能据此断言客户长期为什么购买、持续付费意愿、ROI 或规模化复制已经被验证。

**技术栈：** TypeScript / Node.js｜React｜Python / FastAPI｜PostgreSQL 16 / pgvector｜Docker Compose｜RAG / 知识库｜Prompt / 指令｜工具调用｜Agent 运行时｜评测 / 回归测试 / 测试框架

- **需求分析：** 第一阶段将核心必需能力收敛为知识库 / FAQ、预约 / 服务意向、Ticket / 人工接管、权限控制和真实业务状态；复杂 Semantic Selector、多 Agent 和更深营销自动化不作为 POC 前置条件，因为当前首先要验证的是线上第一接待能否稳定进入真实门店流程。
- **渠道方案：** 微信接入的意义是进入商家已经存在的私域流量入口；当前已经完成微信真实部署。后续如接企业微信或其他入口，主要增加渠道 / 身份适配层；接 CRM 或其他业务系统则主要通过业务接口 / 适配层扩展，尽量不重写 Agent 核心运行时。
- **方案沟通：** 将证据治理翻译成“这个回答是不是来自当前门店可以使用的信息”；将权限控制翻译成“Agent 能理解用户想退款，不代表它有权真正退款”，让技术边界转化为业务方能理解的自动化边界。
- **风险识别：** 客户未必会主动问按权限范围回读、租户隔离或迟到事件，但最终会以“为什么说创建成功系统里却没有”“为什么看到别的门店数据”等方式暴露，因此这些底层约束需要在方案阶段提前处理。
- **POC 验收标准：** 不接受“效果不错”或单一 90% 准确率作为完整验收，而将正常回答、无答案、歧义场景、权限、真实业务动作、人工接管和系统集成分开判断，因为不同错误类型的业务成本完全不同。
- **POC 交付：** 已完成微信部署和实体本地生活门店 POC，门店开始实际使用；长期客户成功、商业化成交、规模化复制和上线后业务提升仍待后续验证。
- **验收：** 区分“系统可用”“门店开始使用”“客户长期使用 / 付费”三个层级，后两项继续通过使用反馈、业务指标和商业过程验证。
- **系统集成：** 核心运行时尽量保持稳定；接渠道主要变化渠道 / 身份适配层，接 CRM / 业务系统主要变化业务接口 / 适配层，再根据现场问题扩展轻量业务流程，而不是为每个客户重做一套 Agent。
- **技术沟通：** 能继续讨论 Prompt、RAG、API、数据库、工具调用、权限控制、Agent 运行时和评测等具体实现问题，同时把这些限制重新翻译成业务方可理解的方案边界，并在真实 POC 中用验收案例而不是技术术语本身证明方案是否成立。

**项目状态：** 已完成微信部署与实体本地生活门店 POC，门店开始实际使用；长期客户留存、商业付费 / 成交闭环、规模化复制、生产环境 SLA 和业务 ROI 仍待验证。
