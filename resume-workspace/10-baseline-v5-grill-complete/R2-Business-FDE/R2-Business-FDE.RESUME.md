## 个人总结

具备从复杂业务环境中识别需求、判断关键约束、拆解方案、推进交付并持续验证的经历。早期在电商和项目经营中长期处理市场、产品、平台商务、供应链、投流、达人 BD 和跨团队协作；后续在淘天 Data Agent 场景中进一步承担业务规则理解、业务上下文对齐、执行转化、QA 与反馈闭环，将上游要求转化为下游可稳定执行的标准和流程。

数字前台 Agent 从小型门店 / 服务型商家的**线上第一接待缺口**出发：线下已有人工接待，但微信等私域入口中的重复咨询、服务状态、预约意向和异常问题仍高度依赖人工即时处理，私域流量缺少稳定承接。

第一阶段先解决 **有人来能接住、常见问题能回答、预约 / 线索不丢、复杂问题有人接管**，再补齐知识库 / 证据、权限控制、真实业务状态、系统集成、验收标准和回归机制。当前已经形成**需求分析 → 方案设计 → 系统集成 → 微信真实部署 → 实体门店 POC → 实际使用**的连续交付链路；现场验证重点也从“工程侧能否跑通”转向“真实门店业务流程能否承接、异常能否转人工、业务状态是否真实发生”。渠道层与 Agent 运行时保持解耦，后续根据真实门店问题逐步扩展轻量能力。

## 工作经历

### 杭州人瑞网络科技有限公司｜评测专家（淘天 Data Agent）｜2025.09–2026.06

- **业务需求理解与执行转译：** 承接上游业务文档、数据口径和任务要求后，先结合真实案例理解规则的适用范围和执行难点，再完成必要对齐，将上游业务要求转化为 BPO 可稳定执行的判断标准、案例和培训内容。
- **需求缺口与边界识别：** 新任务实际放量前主动识别规则定义不清、场景覆盖不足、业务上下文缺失或判断空间过宽等问题，并将关键疑问集中反馈上级确认，避免问题在大规模执行后才暴露。
- **问题诊断与方案调整：** 对抽检和复杂 Bad Case 中重复出现的问题，结合案例、执行理解和规则本身判断问题更偏向业务知识、规则边界还是执行流程，再推动相应的说明、示例、培训和执行方式调整。
- **上下游协作与项目推进：** 在上级和 BPO 执行团队之间承担业务要求理解、任务说明、培训、QA 和问题反馈；无法稳定裁定的复杂案例整理后向上级确认，并持续同步任务阶段和待确认事项。
- **交付规模与质量结果：** 单项任务 BPO **10+ 人、每周约 5,000–10,000 条**；累计参与沉淀 **10+ 份 SOP / 规则 / 执行文档**，部分任务一致性约 **80%→95%**、复杂任务约 **60%→85%**。
- **版本效果与数据观察：** 参与执行层灰度桶 / A/B 测试及数据取数，结合 DAU、CTR、转化、业务水位观察版本效果和异常反馈。

## 项目经历

### 数字前台 Agent｜需求分析 → 方案设计 → 微信部署 → POC 交付

**项目背景与业务问题：** 很多实体商家线下已经有人员接待，但微信等私域入口存在明显线上承接空白；用户进入私域后，重复咨询、服务状态、预约意向和异常问题仍高度依赖人工即时处理。核心问题是**已有私域流量缺少稳定的线上第一接待能力**。

产品因此先收敛为：

**私域入口 → 第一接待 → 知识库 / FAQ → 预约 / 线索意向 → 轻量状态 → Ticket / 人工接管 → 人工跟进。**

**技术栈：** TypeScript / Node.js｜React｜Python / FastAPI｜PostgreSQL 16 / pgvector｜Docker Compose｜RAG / 知识库｜Prompt / 指令｜工具调用｜Agent 运行时｜评测 / 回归测试 / 测试框架

- **需求分析：** 第一阶段不重建完整 CRM，也不扩展成全能数字员工，而是先解决“有人能接、常见问题能回答、预约 / 线索意向不丢、复杂问题有人接管”；避免为了展示 Agent 能力无限扩大产品范围。
- **渠道接入：** 微信接入的价值在于进入目标门店已经存在的私域流量入口；因此将渠道 / 身份适配层与 Agent 运行时分开。当前已完成微信真实部署，未来如接企业微信或其他入口，主要替换渠道 / 身份适配层；如接 CRM / 其他业务系统，则主要通过业务接口 / 适配层对接，而证据、权限、业务状态和评测核心逻辑尽量保持稳定。
- **RAG / 知识问答：** 在实现知识库 / RAG 时发现“检索到了”不代表“当前业务可以回答”，因此检索只返回候选证据，再结合租户 / 门店、状态 / 版本和歧义情况决定回答、拒答或转人工。
- **权限控制：** 模型可以理解用户意图并提出动作，但身份、业务范围、能力权限与最终写操作由服务端控制，防止 Prompt / LLM 输出直接获得业务权限。
- **动作验收：** 在实现 Ticket / 人工接管时发现“模型说完成”或“工具被调用”不能证明业务动作真的发生，因此要求服务端完成权限检查、持久化和按权限范围回读后才确认成功，把 Demo 中的“看起来能用”转成可验证业务结果。
- **系统集成：** 已形成 React + Node、HTTP、PostgreSQL、Docker，以及内部 FastAPI / pgvector 候选证据服务的跨服务集成；交付验证不止检查 Docker 是否能启动，还覆盖干净环境、依赖启动、数据库迁移、重启后状态保持、权限隔离和核心业务流程，避免把“本机能跑”误判为可交付。
- **POC 交付：** 已完成微信部署、实体本地生活门店 POC 并开始实际使用，交付从内部 Demo / 工程验收进入门店业务流程验证；长期稳定性、规模化复制、商业结果和上线指标仍需持续验证。
- **POC 验收：** POC 不以“模型能回答”作为单一成功标准，而分别检查正常回答、无答案 / 歧义、权限隔离、真实状态写入、异常转人工和关键系统集成；其中“回答正确”和“业务动作真正发生”分开验收，避免语言层通过掩盖业务状态失败。
- **RAG 验证：** 当前 pgvector / FastAPI / Node 集成能够证明跨服务与向量链路打通，但不等于真实业务场景下的检索质量已通过；Hosted Embedding、真实门店分布下的检索质量与长期稳定性仍需继续用真实 Query / Bad Case 验证。
- **后续迭代：** 第一接待稳定后，再根据真实门店现场暴露的问题决定是否增加服务提醒、定时触达和私域促活等轻量功能，而不是预先构建复杂 CRM / 营销系统。

**项目状态：** 已完成微信部署与实体本地生活门店 POC，门店开始实际使用；长期稳定性、规模化复制、生产环境 SLA、Hosted Embedding / 业务场景检索质量、复杂企业系统集成及商业化结果仍待持续验证。
