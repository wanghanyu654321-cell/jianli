# 2. 浙江朗臻网络科技有限公司
## 京东电商运营 → 宠物项目管理｜2022.03–2024.07

### FCTM-LZ-01｜0→1 第一原则：先定市场，再定商品和打法
新商品 / 新业务从 0→1 时，第一优先不是直接投流、做内容或改页面，而是先判断市场机会。会结合市场整体数据、搜索需求、关键词增长、竞争情况及推广 / 经营数据判断值得进入的方向。

市场选择通常优先：
- 寻找仍在快速增长、供给存在补充空间的细分市场；
- 观察增长中的细分关键词，把关键词变化作为需求变化的信号之一；
- 不优先用同质化产品直接进入高度成熟红海；
- 如果进入红海，先寻找产品差异化。

责任边界：这是本人实际经营判断方式，不写成公司级市场战略负责人。

### FCTM-LZ-02｜搜索策略：先细分词，再扩大到大词
单品链接从 0→1 起盘时，会先寻找与产品和需求匹配的细分搜索词，在相对可控的竞争环境中建立有效数据和表现，再根据结果扩大关键词范围，逐步进入更大的核心行业词竞争。

涉及：
- 搜索热词 / 长尾词；
- 商品标题；
- 详情页属性；
- 搜索排名和经营数据。

结果：
- 核心商品搜索排名由百名外提升至类目前 10。

边界：
- 可写搜索优化和经营策略；
- 不写搜索算法研发。

### FCTM-LZ-03｜搜索词同时用于市场变化判断
搜索词不只用于 SEO / 排名优化，也用于观察市场需求变化。关注哪些细分关键词正在增长、哪些需求从小众向更大市场扩散、哪些品类已经高度成熟，并将这些信号作为产品方向和经营策略的输入之一。

### FCTM-LZ-04｜推广数据用于区分流量问题与产品 / 链接问题
商品推广后会结合经营数据判断问题发生在哪个环节，而不是默认“投流不够”。

可能继续判断：
- 流量；
- 点击；
- 转化；
- 商品本身是否符合需求；
- 链接是否具备继续放大的基础。

如果判断产品或链接整体难以起量，会考虑：
- 新产品 / 测品；
- 调整产品方向；
- 主图、图文、详情页、链接内容优化；
- 店铺内容优化；
- 重新制定营销策略。

### FCTM-LZ-05｜独立单 SKU 经营结果
另一核心单 SKU：

边界：
- 与“搜索排名百名外 → 类目前 10”是两个独立事实；
- 未证明属于同一商品或单一因果链，不得强行合并。

# 3. 杭州今宜商贸有限公司
## 抖音项目代运营｜2024.11–2025.07

### FCTM-JY-01｜项目属于新盘 0→1，不是成熟差盘救火
同一账号月 GMV 约 `7 万`对应新盘早期业务规模，不是成熟账号经营衰退后的结果。

后续同一账号：
- 新盘早期月 GMV 约 `7 万`；
- 接手后首月约 `43 万`。

正确解释：新盘从 0→1 起量。

禁止解释：“成熟账号经营差，被接手后救回”。

### FCTM-JY-02｜起盘第一优先：先补内功，再用投流放大
进入项目初期先检查：
- 视频素材；
- 直播环境；
- 直播机位；
- 主播话术。

发现基础环节未达到预期后，优先调整底层内容和直播承接，而不是先扩大投流。

判断原则：`先让内容 / 转化内功达到基准线 → 再用投流放大`

### FCTM-JY-03｜从货架 / 搜索逻辑切换到内容优先逻辑
传统电商更依赖搜索、链接、主图、详情页和货架承接；进入抖音后，需要重新适应连续视频和直播的信息表达。

会重新考虑：
- 视频结构；
- 信息密度；
- 场景切换；
- 转场节点；
- 爆点；
- 用户在短时间内获取的核心信息。

小红书内容测试经验可以部分迁移，但不把小红书、传统电商和抖音玩法写成完全相同。

### FCTM-JY-04｜产品定位先于内容表达：玉米包案例
市场常见定位偏“宝宝辅食”。当时观察到健身轻食整体市场数据持续增长，因此重新调整目标人群和卖点：
- 健身轻食；
- 营养健康；
- 方便易食。

事实链：`市场增长数据 → 选择增长方向 → 调整目标人群 / 产品定位 → 内容表达`

### FCTM-JY-05｜把抽象卖点转成视觉场景
对于“营养健康、方便易食”等抽象卖点，会继续转成用户可直接感知的画面。

玉米包案例中，刚制作完成、表面焦化、金黄色泽、冒热气的状态能够强化：
- 食欲；
- 新鲜感；
- 即时食用感。

因此将卖点继续转化为视频 / 直播视觉表达。

### FCTM-JY-06｜直播与视频素材承担不同验证作用
电商侧单纯依靠短视频逐条测试反馈较慢，因此会利用直播较快验证商品、卖点、话术和用户反应。

同时短视频素材通过多个引流直播间计划并行测试；素材中验证有效的表达和卖点，再反哺直播间。

### FCTM-JY-07｜从短视频有效画面迁移到直播双机位
视频素材中发现刚出锅、冒热气的玉米包视觉表现较好后，将这一视觉爆点迁移至直播间。

本人提出 / 设计 / 指导双机位方案：
- 一个机位承担正常直播和商品讲解；
- 一个机位持续展示新制作完成、刚出锅、冒热气的玉米包。

通过不断新做、持续实拍，让直播间持续保留产品最具吸引力的视觉状态。

边界：
- 本人负责方案提出、设计和指导；
- 不写本人承担全部拍摄技术执行。

### FCTM-JY-08｜CTR / CVR 组合用于定位链路问题
不会孤立看单个指标。

- `CTR 高、CVR 低`：前端内容能吸引进入，但后续内功 / 承接不足，优先检查直播内容、主播话术、商品表达等；
- `CTR 低、CVR 高`：进入的人群相对精准，但视频爆点和卖点表达不足，当前内容难以扩大有效人群，需要优化前端表达。

### FCTM-JY-09｜归因优先检查自身可控因素
素材点击不错但直播间接不住时，优先排查：
- 视频是否太泛；
- 人群是否不够精准；
- 卖点是否匹配；
- 直播内容是否一致；
- 主播承接能力。

原则：`先检查自身内容和执行 → 再考虑外部因素`

### FCTM-JY-10｜统一数据口径 + 控制变量 + A/B 缩小问题
面对多个可能变量时，会：
1. 设定锚点；
2. 保持数据口径一致；
3. 尽量保持其他环境不变；
4. 改一个变量；
5. 比较结果；
6. 缩小问题范围。

例如当商品、人群画像、视频卖点没有明显问题时，更换主播观察结果变化；如果其他条件基本一致而主播变化带来明显差异，则进一步判断主播承接能力。

边界：可写控制变量 / A-B 验证习惯；不夸张成严格科研实验设计。

### FCTM-JY-11｜本人直接承担投流判断
今宜项目中的投手职责由本人承担，并使用巨量千川等投放链路。

会结合：
- CTR；
- CVR；
- ROI；
- 素材表现；
- 直播承接；
- 当前业务目标；

判断：
- 是否继续投；
- 是否放量；
- 哪个环节优先调整。

禁止写：“协同投手调整投流”。

### FCTM-JY-12｜主播执行：核心标准统一，细节允许弹性
团队包含全职和兼职主播。

- 全职主播：合作稳定，可围绕数据持续调整；
- 兼职主播：通常按既定话术执行，允许在不偏离核心卖点 / 业务边界的前提下做细微调整。

最终以实际数据效果判断，不以个人偏好作为唯一标准。

### FCTM-JY-13｜编导方案：数据方向与现实执行共同决定
当编导认为某个方案难拍：
- 先尝试复刻已验证有效的方向；
- 确实难以实现时，寻找替代表达方式；
- 不因“难拍”直接放弃已有数据支持的方向；
- 最终以实际执行和数据结果共同判断。

### FCTM-JY-14｜服务开始前先和老板对齐业务目标
项目开始阶段先与老板确认当前优先目标，例如：
- GMV；
- ROI；
- 利润；
- 新盘增长。

不同目标会影响：
- 投放力度；
- 利润容忍度；
- 内容策略；
- 达人佣金；
- 冷启动方式。

事实链：`先确认业务目标 → 再设计服务 / 经营方式`

### FCTM-JY-15｜达人 BD 服务于新盘冷启动
新盘早期：
- 商品缺历史销量和权重；
- 素材验证需要时间；
- 很多达人因缺数据不愿意带。

因此本人主动通过达人合作补初期销量和商品基础权重。达人 BD 是冷启动策略的一部分，不是后期唯一核心渠道。

### FCTM-JY-16｜本人直接开发达人
起盘初期本人直接：
- 加微信；
- 电话沟通；
- 一对一寻找达人；
- 介绍产品；
- 沟通合作方式和条件。

后期项目进入稳定阶段后，没有继续把达人 BD 作为主要日常重心。

### FCTM-JY-17｜达人筛选核心之一：内容与产品契合
由于新盘历史销售数据有限，达人判断会结合：
- 内容与产品的契合程度；
- 粉丝规模；
- 历史销售数据；
- 合作意愿。

产品和达人原有内容是否契合，是影响合作意愿的重要条件。

### FCTM-JY-18｜纯佣条件下提高佣金换取冷启动
项目主要采用纯佣合作，新盘缺销售证明，合作难度较高。

策略：
- 优先 KOC 补基础销量；
- 佣金尽量比同行业高约 `3–5 个点`；
- 粉丝量更大、销售数据更好的达人，可以接受更高佣金。

### FCTM-JY-19｜阶段性让渡达人端利润
冷启动阶段不追求达人渠道单笔利润最大化。只要合作后能够覆盖退款、货损等基本成本底线，可以接受达人端少赚，用短期利润让渡换取：
- 初期销量；
- 商品权重；
- 冷启动速度。

### FCTM-JY-20｜达人合作结果
- `单月达人合作销售额合计 10 万元+`。

边界：
- 不是累计 10 万+；
- 不升级成全量 KOL 资源盘。

### FCTM-JY-21｜另一独立账号经营结果
另一独立账号负责期间：
- 单月 GMV 峰值约 `152 万`。

边界：
- 与 `7 万 → 43 万`账号分开；
- 不合并为同一增长曲线。

### FCTM-JY-22｜约 6 人直播团队协作
协同约 `6 人`直播团队，工作覆盖：
- 策略；
- 目标拆解；
- 排期；
- 培训协同；
- 跟播；
- 投流；
- 内容；
- 数据；
- 复盘。

边界：项目协作规模，不写全部行政直管。

### FCTM-JY-23｜SOP 是问题解决后的沉淀，不是工作主线
今宜存在较多 SOP / 标准化流程，但大量属于行业常见执行方式，不无限拆表格、模板和日报。

当前主线中明确保留：
- 达人筛选；
- 达人触达；
- 合作推进等 SOP / 流程沉淀。

原则：对反复出现且值得标准化的问题沉淀流程供团队复用，母版重点仍然是 `实际问题 → 判断 → 解决 → 验证`。

### FCTM-JY-24｜店铺与经营数据分析
当前主线既有事实保留：
- 参与店铺评分分析；
- 参与流量、营销、交易数据分析；
- 参与推广 / 大促策略分析。

边界：写参与和分析，不补未确认增长数字。

### FCTM-JY-25｜需求清单、优先级、排期与阶段检查
今宜代运营项目中，会把业务目标继续拆成需求 / 事项清单，结合项目阶段和经营目标判断优先级，安排内容、直播、投流等工作的排期，并在不同阶段做检查和复盘。

边界：
- 可写需求梳理、优先级管理、项目排期和阶段检查；
- 不自动升级为传统产品经理的 PRD / Roadmap Owner。

### FCTM-JY-26｜面向合作方的运营方案汇报
项目代运营过程中，会围绕业务目标、阶段方案、当前数据、问题判断和后续安排向合作方做运营方案 / 项目进展汇报，并根据沟通结果继续推进执行。

边界：
- 属于运营方案和合作方沟通；
- 不写成 AI 产品 Demo、POC、技术售前或客户 AI 交付。

# 4. 杭州人瑞网络科技有限公司
## 评测专家｜服务淘天 Data Agent｜2025.09–2026.06

### FCTM-RR-01｜评测范围
参与：
- Query；
- Data Agent 输出；
- 召回结果；
- 商品相关性；
- Badcase 分类 / 归因；
- QA；
- 争议 Case；
- 规则治理。

无法直接裁定的争议 Case：提交正式员工确认。

边界：不写最终业务裁决权。

### FCTM-RR-02｜团队 / 个人任务规模
- 团队 `10+ 人`；
- 每周约 `5,000–10,000` 条任务；
- 个人日处理约 `100–120` 条；
- 常规抽检约 `10%`。

### FCTM-RR-03｜一致性和文档结果
- 部分任务一致性约 `80% → 95%`；
- 复杂任务一致性约 `60% → 85%`；
- 团队累计沉淀 `10+ SOP / 规则 / 执行文档`，本人负责 / 参与其中一部分。

边界：
- “部分任务”限定词必须保留；
- 一致性 / 执行正确率改善不写成模型准确率；
- `10+` 是团队沉淀规模，不写成本人独立完成 10+ 份。

### FCTM-RR-04｜接收上游文档后先理解和对齐，不直接转发
新任务通常由正式员工提供业务文档、数据口径、规则或任务要求。本人先完成理解，再与正式员工对齐：
- 数据口径；
- 业务规则；
- 判断边界；
- 疑问点。

不会将上游文档原样直接分发给 BPO。

### FCTM-RR-05｜下发前必须自己先实际跑一遍
向 BPO 分发新的任务 / 规则前，本人会先实际执行一遍，用真实 Case 检查：
- 文档是否足够可执行；
- 是否有逻辑缺口；
- 是否有定义不清；
- 是否有前后规则冲突；
- 是否有过宽的判断空间；
- 是否依赖但未提供的行业知识 / Context；
- 实际 Case 是否存在文档未覆盖情况。

流程：`文档 → 自己做 → 找问题 → 对齐 → 再分发`

### FCTM-RR-06｜提前集中整理疑问，减少后期返工
理解和试做过程中会主动识别逻辑缺失 / 执行困难，并尽量把疑问一次性整理后向正式员工集中确认，而不是等 BPO 大规模执行后再逐项暴露。

### FCTM-RR-07｜承上启下的信息转译与执行承接
实际链路：
`正式员工业务目标 / 规则 / 数据口径`
→ `本人理解 / 试做 / 找缺口 / 对齐`
→ `转成下游可执行边界 / 培训`
→ `BPO 执行`
→ `QA / 问题反馈`

边界：可写承上启下和执行承接；不写正式项目 Owner。

### FCTM-RR-08｜BPO 错误可能来自行业 Context 缺失
实际发现，一些错误不是简单“不熟规则”，还可能来自行业知识 / 背景不足，例如：
- 商标；
- 品牌；
- 品牌区分；
- 商品和业务背景。

因此规则培训需要在必要时补足完成当前任务所需的 Context。

### FCTM-RR-09｜通过日常 / 一对一沟通发现隐性理解问题
正式会议中，执行人员未必会主动表达困难。除会议答疑外，也会通过日常的一对一 / 非正式交流了解：
- 实际哪里难；
- 哪个概念不清楚；
- 哪类 Case 容易疑惑。

用于发现会议中没有暴露的理解缺口。

### FCTM-RR-10｜培训前先定“大边界 + 必要 Context”
培训不是无限补知识。先明确：
- 任务到底判断什么；
- 哪些属于范围；
- 哪些不属于；
- 哪些可以自行判断；
- 哪些需要升级；
- 当前任务真正需要哪些行业 Context。

目标是避免执行人员理解越来越宽、越做越散。

### FCTM-RR-11｜培训同时优化效率和正确率
培训 / SOP / 任务说明同时考虑：
- 正确率：能否达到正式员工设定的要求；
- 效率：是否存在不必要信息、判断步骤是否可以更简单、Context 是否只补充任务真正需要的部分。

目标：`让任务更容易执行，同时更接近目标正确率`

### FCTM-RR-12｜从执行人员的思考路径反向优化任务链路
发现错误时，不只指出“判错”，还会理解：
- 对方看到了什么；
- 为什么会这样推导；
- 从哪一步开始偏；
- 是行业知识不足；
- 规则理解太宽；
- 还是流程本身容易产生误导。

再决定调整：
- Context；
- 规则；
- SOP；
- 示例；
- 判断边界；
- 执行步骤。

### FCTM-RR-13｜抽检用于 QA + Root Cause + Workflow Feedback
抽检发现问题后，会：
1. 找到对应执行人员；
2. 还原其理解路径；
3. 判断偏差发生位置；
4. 区分知识、规则、边界或流程问题；
5. 补 Context / 规则 / SOP；
6. 必要时缩小判断范围；
7. 通过后续执行继续观察。

### FCTM-RR-14｜规则过宽时主动收窄边界
如果执行人员频繁“跑歪”，会判断是否因为规则解释空间太大，并通过：
- 收窄边界；
- 补充具体说明；
- 增加必要 Case；
- 明确不能自行延伸的区域；

再通过后续抽检观察效果。

### FCTM-RR-15｜进度、问题与待确认事项持续向正式员工同步
执行过程中持续同步：
- 当前进度；
- 任务阶段；
- 已发现问题；
- 待确认事项。

目标：
- 让正式员工持续掌握工作推进状态；
- 保持过程可持续、可追溯。

### FCTM-RR-16｜业务结果与版本效果观察
接触部分业务结果和版本效果指标，包括：
- DAU；
- CTR；
- 转化相关指标；
- 灰度流量；
- 业务水位；
- 按时间维度观察指标变化和版本表现。

参与：
- 版本效果观察；
- 异常结果汇总；
- 问题反馈；
- 结合指标随时间变化判断是否存在异常或需要进一步排查的问题。

边界：
- 不写完整线上权限；
- 不写独立 A/B 分桶 / 实验 Owner；
- 不写独立线上策略负责人；
- `eCTR / pCTR / eCVR / pCVR / UVCTR / Lift` 等具体指标名称目前记忆未完全确认，暂不作为正式事实写入。

### FCTM-RR-17｜搜索 / 推荐链路理解
接触并理解：
`Query 预处理 / 理解 / Rewrite → Recall → Filter → Coarse Rank → Fine Rank → Rerank → SERP → Feedback / A-B`

并使用 / 理解 L1 / L2 / L3 相关性分级。

边界：写“理解 / 接触”；不写亲自实现搜索排序算法。

### FCTM-RR-18｜评测类目补充与 Badcase 分类
正式任务框架通常由正式员工确定，本人不是整套 Task / Rubric 的最终 Owner；但在实际试做和执行过程中，会根据 Case 补充评测类目 / 判断分类，并对 Badcase 做相对稳定的分类和归因，用于后续统计、规则补充和培训。

边界：
- 可写“参与定义 / 补充评测类目”“Badcase 分类体系”；
- 不写独立设计完整评测体系或最终 Rubric Owner。

### FCTM-RR-19｜规则修改后的复测与质量验证
规则、SOP、示例或执行方式调整后，会继续通过复测 / 后续抽检比较调整后的执行结果，确认问题是否真正改善。

该闭环是部分任务一致性约 `80% → 95%`、复杂任务约 `60% → 85%` 等质量改善过程的一部分。

边界：
- 可以表达“修改后复测 / 再验证”；
- 不将上述数字升级为模型准确率或由本人单独造成的结果。

### FCTM-RR-20｜Agent 行为评测不只限于 Query / Recall
实际评测中还接触 / 判断过：
- 多轮上下文是否被正确理解和延续；
- 工具调用结果是否符合当前任务；
- 执行步骤是否完整；
- 必要信息是否收集齐；
- 最终回答是否真正解决用户 Query / 业务问题。

边界：
- 可作为 Agent Behavior / Workflow Quality 的评测证据；
- 不写本人实现 Agent Runtime、Tool Calling 或多轮系统。

### FCTM-RR-21｜基础 SQL 阅读、查询取数与 Data Agent SQL 能力背景
本人能够：
- 阅读简单 SQL；
- 做基础查询取数。

服务的 Data Agent 具备自动生成 SQL 指令的能力；日常接触到的业务数据通常经过脱敏处理。

边界：
- 可写基础 SQL 阅读 / 查询取数；
- 不写 SQL 开发、数据工程、复杂数仓建模；
- Data Agent 自动写 SQL 是所服务系统能力，不是本人实现的功能。

### FCTM-RR-22｜反馈后的修改跟进与再验证
向正式员工反馈规则 / 产品 / 系统侧问题后，部分事项会继续跟进修改后的结果并参与补充验证。

责任边界：
- 通常以补充、反馈、验证角色参与；
- 不写独立产品 Owner、Roadmap Owner 或最终上线负责人。

### FCTM-RR-23｜评测资产和文档类型
团队沉淀内容不只包括 SOP，还包括任务说明、评测标准 / 判断说明、Case / 示例、FAQ、问题清单等不同形式；本人负责或参与其中一部分内容的整理、补充和维护。

边界：
- 团队资产与本人负责部分分开表达；
- 不写本人独立建设全部评测资产。


### FCTM-RR-24｜开放题评测：高低分答案与路径对比
当前评测以开放问题为主，通常不存在唯一标准答案。实际判断中会结合既有指标选取高分 / 低分答案进行对比，并查看不同 Layer / Path 的差异，重点观察哪些关键节点造成最终质量差异，再把稳定差异总结为后续可执行的规则或判断口径。

当前所说 Layer / Path 对比，主要是比较高分与低分样本在不同处理路径上的差异，不写成已经存在统一标准轨迹或单一 Gold Path。

边界：
- 可写高分 / 低分答案对比、路径差异分析、关键节点归因和规则沉淀；
- 当前不是依靠完整人工逐条评审覆盖所有开放题；
- 不写已经建立统一自动化轨迹评分平台。

### FCTM-RR-25｜结果指标与轨迹评测需要分层
简单埋点更适合记录运行指标，例如：
- 首 Token 延迟；
- 工具调用数量；
- KV Cache 等运行参数。

这类指标只能说明运行状态，无法单独判断 Agent 的决策过程是否合理。

轨迹评测需要 Agent 框架提供结构化 Trace，至少能够看到：
- 意图识别；
- 规划 / 决策节点；
